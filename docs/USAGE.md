# 使用手册

## 安装

1. 打开 `edge://extensions/`（Chrome 用 `chrome://extensions/`）
2. 打开右下角「开发人员模式」
3. 点「加载解压缩的扩展」，选择本目录（或 `dist/unpacked/`）
4. 首次加载会自动打开设置页，先填求职画像

不需要装任何依赖，不需要 Node，不需要 Python。扩展本体就是 `manifest.json` + 几个 js 文件。

## 首次配置：七项画像

设置页里这七项决定打分的准确度，按影响从大到小排：

| 项 | 例子 | 说明 |
|---|---|---|
| **标题核心** | `EMC、电磁兼容、硬件测试` | **最容易漏、影响最大**。标题里一个都不含的岗位直接封顶到「跳过」，挡标题级误判全靠它 |
| 偏好词 | `EMC、电磁兼容、可靠性、电源` | 命中加分，可以有多个 |
| 回避词 | `销售、倒班、夜班` | 命中减分；标题命中直接封顶到「待看」，不自动投 |
| 排除词 | `外包、食品、劳务派遣` | 命中直接出局 |
| 目标城市 | `宁波、杭州、苏州` | 指定城市码，也用于「换城市」 |
| 薪资下限 | `8`（即 8K） | 低于下限直接跳过 |
| HR 活跃门槛 | `14`（天） | 超过这么多天没活跃就跳过；填 0 关闭。详见下面「HR 活跃度」 |

「标题核心」空着时，报告第一行会提示 `标题核心（未填）`。实测后果：`EMC仿真工程师`、`emc工程师 18-25K` 这类标题会被算成高分（72 分），因为它们靠偏好词命中了 `EMC`，而标题里其实写的是「仿真」。

## 扫描打分

```
1. 打开 BOSS 岗位列表  → https://www.zhipin.com/web/geek/jobs?query=EMC
2. 点悬浮面板「扫描打分」→ 每张卡右上角出现分数徽章
```

| 徽章 | 含义 | 会不会被自动投 |
|---|---|---|
| 绿色 + 分数 | 推荐（≥ `approve` 阈值） | 会 |
| 橙色 + 分数 | 待看（介于 review 与 approve 之间） | 不会 |
| 灰色 + 分数 | 跳过 | 不会 |

扫描阶段**完全不点击**，只读 DOM、只画徽章。扫完点「报告」能看到每张卡的判定依据。

## HR 活跃度：两周没上线的直接跳过

BOSS 不写「HR 最后一次上线是几号」，只写一个档位。这些档位会被换算成「最多多少天前活跃」，超过门槛（默认 14 天）就跳过：

| 卡片上写的 | 换算 | 门槛 14 天时 |
|---|---|---|
| 刚刚活跃 / 今日活跃 / 当前在线 | 0 天 | 放行 |
| 昨日活跃 | 1 天 | 放行 |
| 3日内活跃 | 3 天 | 放行 |
| 本周活跃 | 7 天 | 放行 |
| 2周内活跃 | 14 天 | 放行（等于门槛不算超期） |
| 本月活跃 / 1月内活跃 | 30 天 | **跳过** |
| 半年前活跃 / 一年前活跃 | 180 / 365 天 | **跳过** |

**两处判定，都在「点沟通」之前**：扫描时读卡片（不合格的岗位连点都不会点），投递时再读一次详情页——有些卡片只写「近期活跃」这种模糊话，详情页里才是「1月内活跃」。详情页这一路在「读 JD 停留」之前就返回，能省掉几秒白等。

**认不出就放行。** `近期活跃`、单独的「活跃」、结构变化读不到——这些都不算不活跃。理由很简单：一次选择器失配如果被当成「HR 都不活跃」，用户看到的是「今天一个岗位都不推荐」，比误投十个更糟。所以这是**黑名单式**判定，不是白名单。

被跳过的岗位长这样（徽章与报告里都有）：

```
0 跳过    ← 徽章悬浮提示：HR 久未活跃：本月活跃
```

报告里还会写一行 `HR 活跃门槛 14 天`，贴给别人时不用再问「你设的多少」。

想放宽就调大（比如 30，只拦「半年前活跃」），想关掉填 0。

**怎么确认真的读到了活跃度**：点扩展图标 →「页面诊断」，找这一行——

```
卡片带活跃度 18/20（例：3日内活跃、本周活跃、本月活跃）
```

`0/20` 说明这个版本把档位写在别的地方（或者改成了「近期活跃」这类模糊说法），此时活跃度筛不生效，但**也不会误杀**。把这一行发出来，就能知道该不该加新的档位写法。

## 开始投递

点「开始投递」→ 二次确认 → 按分数从高到低逐个处理。

每份的流程是：**先直接请求详情页拿 JD** → 停留 2~5 秒 → 用 JD 全文重新打分 → 不达阈值就跳过（此时连卡片都没点）→ 达阈值才找沟通按钮。

拿 JD 的第一条路是 `GET /job_detail/<jobId>.html` 再本地解析 `.job-sec-text`：不点卡片、不等右侧面板、不跳页，落地页结构怎么变都不影响读 JD。请求不到（未登录 / 被安全校验 / 结构变了）才退回「点开卡片读右侧面板」。

### 两个上限不是一回事

- **单轮上限 8 份**：点一次「开始投递」最多投 8 个。日志里那句「本轮已投满 8 份」说的是这个。扫出 18 个推荐却只投了 8 个，剩下的没丢，它们还在列表里。
- **每日上限 30 份**：今天所有轮次加起来的天花板，到点记 `daily_cap` 停到明天。

投满 8 份后**不用刷新页面**，直接再点一次「开始投递」就是新一轮：已投的会被跳过，从第 9 个接着投。嫌 8 份太少，去设置页「限额 → 单轮上限」调大（不能超过每日上限）。

### 节奏：三个档位

设置页「节奏」有三个按钮，点一下把间隔、休息、读 JD 停留八个参数一起改掉，旁边直接显示「跑满 8 份约 X 分钟」：

| 档位 | 间隔 | 每几份休息 | 休息时长 | 读 JD | 8 份大约 |
|---|---|---|---|---|---|
| 快 | 5~12 秒 | 10 | 30~60 秒 | 1~3 秒 | 1 分钟 |
| **标准（默认）** | 12~30 秒 | 8 | 1~2.5 分钟 | 2~5 秒 | 3.5 分钟 |
| 保守 | 25~70 秒 | 5 | 2~6 分钟 | 3~9 秒 | 10 分钟 |

老版本默认「保守」，8 份要跑十分钟，慢到人以为卡死，所以默认改成「标准」。要更快就点「快」——**但风控看的是投递总量和节奏突变，不是这几秒**，真正管用的仍然是把单轮上限压下来。

> 升级后已有的 `config` 会留在 storage 里，档位按钮不会自动改写它。想用新默认值，手动点一次「标准」。

## 换一批：怎么在网页上「刷新出更多岗位」

BOSS 网页没有「刷新岗位」按钮，能拿到新岗位的路只有这几条。点一次「换一批」，扩展按代价从轻到重自动试：

| 顺序 | 动作 | 什么时候有效 |
|---|---|---|
| ① | **滚动列表到底，触发懒加载** | BOSS 的主机制，绝大多数情况靠这一招 |
| ② | 点「加载更多 / 查看更多」 | 这一版确实有追加式按钮 |
| ③ | 点「下一页」 | 列表是分页式的 |
| ④ | 切「最新发布」排序 | 当前搜索已翻完，换排序换一批结果 |
| ⑤ | **换关键词 / 换城市重新搜** | 前四样都没有——这是唯一确定能拿到新岗位的路 |

①放在第一位是有原因的：BOSS 的岗位列表是**无限滚动**，本来就没有「下一页」。先去找按钮，等于在找一个不存在的控件。列表底部出现「没有更多了」时直接跳过 ①。

判断「有没有真的换到」只看一个证据：**卡片里出现了新的 jobId**。按钮的 disabled 状态、滚动高度、类名都不靠谱，没有新卡片就当这一招失败，直接试下一招——所以不会出现「提示成功但其实没动」。

前四招都没新岗位时会弹一个选择框，而不是问「要不要刷新」：

```
这一批已经到底了
这个条件下 BOSS 没有更多岗位了，刷新页面只会重新拉同一批。
换条件才会有新岗位：
  [ 换关键词：电磁兼容 ]   ← 主按钮，默认动作
  [ 换城市：苏州 ]
  [ 刷新本页（还是这一批）]
  [ 取消 ]
```

- **换关键词**：从画像的偏好词 / 标题核心词里取下一个（EMC → 电磁兼容 → 可靠性 → …，到末尾回到第一个），保留经验、学历、规模这些筛选条件，从第一页重新搜，页面加载后自动扫描。
- **换城市**：在画像的目标城市之间轮换，同样保留其余条件；城市名按 BOSS 自己的城市码换算，认不出的城市不给这个按钮（宁缺一个按钮，也不拼无效链接）。
- **刷新本页**：还是同一批，只是可能有新发布的岗位排进来。

**为什么不是直接刷新**：BOSS 的搜索结果是「同一条件 → 同一批岗位」，重载只是把同一页再请求一次。真正决定你看到哪些岗位的是搜索词和城市。

**为什么会说「已经到底了」**：它没有说谎。那一次扫描已经把列表滚到底、把懒加载能加载的都加载完了（`scroll_rounds` 默认 8 轮，连续两轮没有新卡片才停）。比如「宁波 + 3 个经验段 + 2 个学历 + 1 个规模」这种窄条件，BOSS 总共就给你 30 条左右，第 31 条之后真的没有了。这时候唯一能让岗位变新的办法是**改条件**。

## 招呼语：两种模式，必须二选一

### 模式 A：扩展代发（默认）

网页版点「立即沟通」**只会跳到 `/web/geek/chat`，一句话都没发出去**。对方要收到消息，必须有人在输入框里打字并点发送。所以投递的最后一步是这样，任何一步失败都**不算投递成功**：

1. **找输入框**：先按类名（`.chat-input` / `.chat-editor` / `contenteditable`），找不到就按位置兜底——会话面板底部、面积最大的那个可编辑元素。聊天页顶部的搜索框会被排除。
2. **写文字**：`execCommand('insertText')` 走原生编辑管线（受控组件才认）；落空就点一下编辑器再写一次，仍落空则改派发 `beforeinput`/`input`。
3. **发送**：优先点编辑器和它向上 4 层里**可用**的「发送」按钮；按钮不存在或灰着，就**按回车**（`keydown/keypress/keyup` 全套）。
4. **验证**：输入框被清空、消息列表出现这句话、会话多了一条——三条任一成立才算发出。
5. 验证通过才记「已投」并 +1 额度；否则记 `greeting_failed`，下一轮会重试。

只有「文本还留在框里」才会退到上一条更弱的发送方式，所以不会给对方发两遍。

### 模式 B：交给 BOSS 自带自动打招呼

设置 →「招呼语交给 BOSS 自动打招呼」勾上之后，扩展只做三件事：筛选、打分、点「立即沟通」把会话打开，**不再自己写一个字**。

1. 点「立即沟通」→ 跳进 `/web/geek/chat`
2. 等聊天输入框出现——这是「会话真的建立起来了」的证据
3. 再看一眼会话里有没有消息：
   - 有 → 日志 `BOSS 已自动打招呼：xxx`，记录标 `boss_auto`
   - 没有 → 日志 `会话已建立，招呼语交给 BOSS（本条没看到自动消息）`，记录标 `boss_no_msg`

两个标记的区别只有一处：`boss_auto` 确认对方收到了消息，`boss_no_msg` 表示会话建起来了但没看到消息（多半是 BOSS 那边没配自动打招呼）。两种都算「已投」，但报告里分得清。

还有一种情况也处理了：有些版本点「立即沟通」会先弹一个写招呼语的框，里面**已经预填了你在 BOSS 设置里写的招呼语**。勾上这个开关后，扩展不再覆盖它，直接按原样发出；只有框是空的才补一句模板（否则点下去等于发空白消息）。

**为什么必须二选一**：BOSS 的自动打招呼和扩展的代发是两套独立机制。两边都开着，对方会收到两条招呼语——而且扩展还会把它记成自己的功劳。勾上开关后，`sendGreetingInChat` 整条路径直接不走。

判据没有放松：**找不到输入框仍然不算投成**（记 `chat_not_opened`），不会因为「按钮点过了」就记一笔。

## 已投的不会再走一遍

去重不能只看 `jobId`。BOSS 的卡片形态不稳定：有时外层是 `<a href="/job_detail/xxx.html">`，能解析出 `jobId`；有时整张卡是个 `div`，取不到。于是同一个岗位第一次可能存成 `id:xxx`，第二次算成 `tx:标题|公司`，两套键永远对不上——已投的又被投一遍，白等十几秒还多记一笔额度。

所以记录里两套证据都留，`isDone()` 任一条命中就算做过：

| 证据 | 强度 | 说明 |
|---|---|---|
| `jobId` | 强 | 卡片带 `job_detail` 链接时可用 |
| `标题 + 公司` | 兜底 | `jobId` 拿不到或变了时用；公司为空则不启用，避免同标题不同公司被误杀 |

另外三条也算终止态或提前刹车：

- **BOSS 自己标的「继续沟通」**：打开岗位后先看按钮文案，不是「立即沟通」就直接跳过——**此时还没花时间读 JD**，也不用等那几秒。记 `already_contacted`，不占额度。点了它只会弹「是否继续沟通」，既没发新消息，又会被记成一笔成功投递，所以宁可跳过。
- **队列是一次性快照**：每份下手前再查一次，中途投过的不会再走。
- **报告里能看到账**：日志会打「队列里跳过 N 个已投过的岗位」，而不是悄悄少投。

### 扫描报告

```
页面 https://www.zhipin.com/web/geek/jobs?query=EMC&city=101210100

## 本次画像
城市 杭州、苏州、南京
薪资下限 8K
标题核心 EMC、电磁兼容、硬件测试
偏好 EMC、电磁兼容、可靠性、电源
回避 销售、倒班
排除 外包、食品

卡片 26｜推荐 6｜待看 1｜跳过 19
依据 未命中任何偏好词 ×14、标题不含目标岗位名 ×11、命中排除词 ×2

## 推荐 (6)
1.  78 推荐  EMC测试工程师 | 杭州 | 15-25K | 杭州某电子
     ↳ 标题命中：EMC、电磁兼容；薪资 15-25K 符合下限
```

三个区块各自有用：

- **本次画像**：判定用的到底是什么配置。贴在对话里时，对方不用再问「你城市填了吗」。
- **依据分布**：一排「×N」。如果跳过理由全是同一句，说明不是岗位的问题，是词表或搜索词的问题。
- **标题核心（未填）**：这一项空着会直接打一行提示。

三个用途：排查「点了没反应」（看 `findChatButton()` / `readPanel()` 到底有没有命中）、排查「卡片数是 0」（看每个候选选择器的命中数）、给开发者定位（在列表页导出一份、点开岗位后导出一份，差异就是真实的交互路径）。

# 排错手册

## 扫出 0 张卡

所有 DOM 假设集中在 `src/extract.js` 的 `SEL` 表里。先点「页面诊断」看 `## 卡片选择器命中` 一节：如果所有候选都是 0，说明页面结构变了（或者你不在列表页）。改 `SEL` 里对应的选择器，刷新页面重跑。

## 推荐数比上一轮少了很多

先看报告「本次画像」里的 `HR 活跃门槛`，再看「依据」里有没有 `HR 久未活跃 ×N`：

- **有** → 是活跃度这条规则在起作用。门槛设得太小会误伤：BOSS 几乎每个岗位都标活跃度，而「本周活跃」换算下来就是 7 天，门槛填 3 会一次拦掉一大片。默认 14 只拦「本月活跃」及更久，是保守值。
- **没有** → 岗位是被别的规则筛掉的（城市 / 薪资 / 排除词 / 偏好词），往下看具体理由。

## 未读到 JD

日志里这句的形式是：`未读到 JD：xxx（点开后面板没变化，卡片上也没有沟通按钮）`。

先看本轮开头那行 `JD 来自详情页：486 字` 还是 `详情页没取到 JD（http_403 / verify / no_sec），改点卡片`：

- **前者**：直读成功，问题在别处（看后面的失败原因统计）。
- **后者**：BOSS 拦了同源请求，退回面板路径。此时看紧跟的 `可读面板候选 3 个：div.job-detail-box(486字,含JD) / …`。

### 面板有好几个时，别读到一个「永远不变的壳」

页面上带 `job-detail` 字样的元素经常有七八个：外层包裹壳、占位容器、真正的右侧面板。以前只取**页面里第一个**，于是很容易读到一个文本永远不变的壳——表现就是「点了卡片，面板明明变了，脚本却报面板没变化」。

现在把所有候选都收下来，按「**里面真的有 JD 段落** → 文本更短（更内层）」挑一个，`innerText` 只对最终选中的那个算一次（对整页级大容器算 innerText 很贵，而等面板时每 160ms 就要跑一次）。

`可读面板候选 0 个` 说明页面上没有任何一个可见容器含 JD 段落——通常是详情区根本没渲染，或者这个版本压根没有右侧面板。

### 点开卡片没反应时，脚本会自己换目标

原因是**点击处理绑在哪儿，各版本不一样**。老版本把监听挂在整个卡片容器上，点容器就开面板；新版本可能只挂在卡片里的 `<a>` 或标题上，点外层 div 一点反应都没有。

所以现在按顺序试四个目标，每个给一段时间观察：

```
卡片容器 → 卡片外层 li → 卡片标题 → 详情链接
```

后两个必须**拦住默认跳转**（`preventDefault`，不阻断冒泡），否则点一下 `<a>` 就整页导航、脚本上下文被销毁，看起来同样是「没反应」。

四个都不行时，日志会直接打出三条现场信息，报告里还有完整版：

```
点开卡片：试过 4 个目标（卡片容器 → 卡片外层 → 卡片标题 → 详情链接）
  链接 href=/job_detail/xxxx.html target=_blank
  → target=_blank：点了会开新标签页，当前页永远不会变
  页面 [class*="job-detail"] 元素 0 个
```

`target=_blank` 是死路：BOSS 把详情页开在新标签页，当前页的脚本跟不过去。目前不会自动处理这种情况。

`[class*="job-detail"] 元素 0 个` 则说明页面根本没有右侧详情区，那这条流程只能靠卡片自带的「立即沟通」，卡片上也没有就只能手动点。

## 聊天页发不出招呼语

失败时日志会多出 3~4 行现场信息，完整版进报告的 `## 聊天页诊断`：

```
聊天页诊断 /web/geek/chat
可编辑元素 3 个
  div.chat-input 620x88
  div.chat-input-inner 600x60
  input.search-input 180x30
发送键：未找到可用按钮（会走回车发送）
  候选 button.btn-send 「发送」
消息条数：0
```

`可编辑元素 0 个` = 会话没打开或页面结构完全变了；`发送键：未找到` + `消息条数：0` = 选择器全落空但回车仍可能有效。有这段就不用再靠「你那边 DOM 长什么样」猜。

## 薪资显示成 `111-111K`

BOSS 把薪资数字替换成私用区字符 `U+E031~U+E03A`，配自定义字体渲染。默认按顺序映射（`0123456789`）。如果看到明显的异常数字，说明映射顺序不同，去设置页的「高级」里改那 10 位数字。徽章上会标「薪资解密存疑」，这类岗位建议人工看一眼再决定。

## 一次也没投出去，但日志说「已投满」

那是 `appliedSession` 没重置的旧 bug（1.4.5 已修）。现在每轮开头会打一行 `开始新一轮`，计数从 0 起。

# 建议用法

- **第一周把每日上限压到 10**，观察有没有招呼发出去对方收不到的情况
- **准备小号先试**，别拿主号（简历、沟通记录都在上面）当实验品
- **分时段**：上午 10 份、下午 10 份、晚上 10 份，别一口气跑
- **别开 VPN 切 IP**，异常登录比什么都危险
- **投完人工核对 3~5 家**：进聊天页确认对方真的收到了。脚本只能确认「消息发出去了」，确认不了「对方已读」
- **触发验证就停手**，老老实实手动过，别用工具重试
