# 设计与取舍

这份文档记录「为什么这么做」，而不是「怎么用」。想上手请看 [USAGE.md](USAGE.md)，想看分层与数据流请看 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 目标与非目标

**目标**：在一屏几十张岗位卡片里，用**本地规则**判断哪些值得投，然后**克制地**逐个发起沟通，整个过程可解释、可回退、可诊断。

**非目标**：

- 不做海投。单轮 8 份、每日 30 份是硬闸门，不是建议值。
- 不做反检测。遇到验证码 / 安全校验 / 平台上限弹窗一律停手，交给人。
- 不做数据外传。没有后端、没有埋点、没有远程配置，所有配置和记录都在 `chrome.storage.local` 里。

## 为什么是浏览器扩展，而不是 CDP / Playwright

上一版是 Python + Chrome DevTools Protocol。它的可检测面是真实存在的：

| 检测面 | 原理 |
|---|---|
| 协议域启用痕迹 | `Runtime.enable` 会劫持页面的 `console` 对象以投递 `Runtime.consoleAPICalled` 事件，页面可用属性描述符探测出已被改写 |
| 堆栈特征 | `Debugger.enable` 影响 `Error.prepareStackTrace`，异常堆栈会出现非预期帧 |
| 时序侧信道 | `Runtime.evaluate` 引起的执行抖动，可用 `performance.now()` 做统计识别 |
| 启动参数 | `--remote-debugging-port` 在进程命令行里，页面 JS 读不到，但配合本地端口扫描可被发现 |

这些检测在通用风控里不算主流，但**一旦被针对就很容易**。所以改成扩展形态是合理的。

**但要纠正一个流行说法**：评论区那句「用插件，和人手动点一样，不会风控」并不准确。扩展发出的点击事件 `isTrusted` 仍然是 `false`（CDP 的原生鼠标事件反而是 `true`）。真正的差别不在「像不像人点」，而在：

- 没有调试端口 → 少一层环境可检测性
- 复用真实的浏览器、Cookie、IP、设备指纹 → 环境判定这层天然通过
- 不用另起浏览器 → 不会出现「新环境 + 异常登录」

有人说自己投了两万多条没被限，更可能的原因是**分摊到很多天、每天量不大、且做了语义筛选所以点击次数少**，而不是「用了插件」。同一条评论下另一个人「一次性投 150 份就被封」，说的正是这件事：**批量才是主因**。

## 为什么用本地规则打分，而不是调用大模型

三个理由，按重要性排序：

1. **可复现**。同一个岗位、同一份画像，任何时候打分结果都一样。调模型会引入不可复现的抖动，而「为什么这个岗位被判 42 分」是用户唯一会追问的问题。
2. **零延迟、零成本、零外传**。一次扫描 30~80 张卡，本地跑完不到 50ms；简历画像（学校、年限、期望薪资）不需要离开本机。
3. **可解释**。每条判定都能打出「标题命中：EMC、电磁兼容；薪资 15-25K 符合下限」。模型给不出这种句子，而报告的价值全在这些句子上。

规则本身很朴素：偏好词加分、回避词减分、排除词直接出局、薪资不达下限出局、标题不含目标岗位名封顶到「跳过」。真正的工程量不在打分公式，而在**词表能不能覆盖你实际遇到的 JD**——所以设置页把「标题核心」单独拎出来，它是挡标题级误判的最后一道闸。

## 为什么零运行时依赖、零构建

扩展本体就是 `manifest.json` + 几个 js 文件，加载即可用，没有 webpack / vite / TS 编译链。这不是为了炫技，而是为了两件事：

- **改一行就能重载验证**。这类工具的绝大部分时间花在「BOSS 又改版了」上，构建链越短，修选择器的循环越快。
- **审计成本低**。一个能操作你已登录账号的扩展，用户（包括未来的你）需要能一眼看完它到底发了什么请求。几百行无依赖代码可以做到，打包产物不行。

打包脚本 `scripts/build.mjs` 连 `archiver` 都没用，zip 是手写的（store/deflate + central directory），因为整个项目只有一个地方需要 zip。

## 为什么把 DOM 假设集中在一张 `SEL` 表

页面结构会变，改动必须收敛到一个地方。`src/extract.js` 顶部的 `SEL` 表是唯一允许出现选择器常量的位置，其它模块只调函数。

但光有表不够——真实世界里「哪个选择器命中」本身就不稳定，所以每个关键动作都有**多级回退**：

| 动作 | 主路径 | 回退 1 | 回退 2 |
|---|---|---|---|
| 读 JD | 请求 `/job_detail/<id>.html` 解析 `.job-sec-text` | 右侧面板（多候选择优） | 「岗位职责 / 任职要求」文本特征捞 |
| 点开卡片 | 卡片容器 | `li` 外层 → 标题 | 详情链接（`preventDefault` 拦跳转） |
| 找沟通按钮 | 本岗面板内的按钮 | 卡片内按文本找（取最深） | 点开卡片再取面板按钮 |
| 找聊天输入框 | 类名 | `contenteditable` / `textarea` | 会话面板底部面积最大的可编辑元素 |

每一层回退失败都会在日志和报告里留下**现场证据**（试过哪些目标、每个候选多少字、链接的 `href`/`target`），这样「点了没反应」不需要靠猜。

## 为什么去重必须双键

BOSS 的卡片形态不稳定：有时外层是 `<a href="/job_detail/xxx.html">`，能解析出 `jobId`；有时整张卡是个 `div`，取不到。于是同一个岗位第一次可能存成 `id:xxx`，第二次算成 `tx:标题|公司`，两套键永远对不上——已投的又被投一遍，白等十几秒还多记一笔额度。

所以记录里两套证据都留，任一条命中就算做过：

| 证据 | 强度 | 说明 |
|---|---|---|
| `jobId` | 强 | 卡片带 `job_detail` 链接时可用 |
| `标题 + 公司` | 兜底 | `jobId` 拿不到或变了时用；**公司为空则不启用**，避免同标题不同公司被误杀 |

反向的坑也踩过：同名不同岗（同一家公司两个「测试工程师」，`jobId` 不同）被弱键误杀。所以弱键命中的记录里如果自带 `id`，且与当前 `jobId` 不同，就**不算已投**。

## 为什么节流做三个档位，而不是「越快越好」

风控看的不是单次间隔，而是**单位时间内的总量和节奏突变**。把间隔从 25 秒压到 5 秒，风险收益比很差：省下的十分钟换不来几个岗位，却把「异常高频」这条特征显性化。

所以默认是「标准」档（12~30 秒 + ±25% 抖动，每 8 份歇 1~2.5 分钟），并提供「快 / 标准 / 保守」三档一键切换——真正管用的闸门仍然是单轮 8 份、每日 30 份。

## 明确不做的事

- 没有验证码识别、滑块破解
- 没有 UA / 指纹伪造
- 没有代理 IP 池、多账号切换
- 没有「绕过反滥用机制」的任何尝试

这不是能力边界，是产品边界：一个需要靠隐藏自己才能用的工具，不该被做成基础设施。

## 这套东西里真正通用的部分

如果要从这个项目里提炼一条可复用的经验，是这句：**在你不控制的 DOM 上，任何单点假设都会失效，所以每条路径都要有第二方案，并且失败时必须留下可判读的证据。**

具体到工程手段：

- 抽取层与逻辑层分离，前者只输出结构化数据，后者不碰 DOM（因此可以纯 jsdom 单测）
- 多候选容器择优（按「含关键段落 → 文本最短 = 最内层」挑），而不是 `querySelector` 取第一个
- 点击目标链 + 每个目标的观察窗口按剩余时间平摊，避免固定超时把后续目标截断
- 幂等记账：只有拿到「消息真的发出去了」的证据才 `+1`，按钮点过不算
