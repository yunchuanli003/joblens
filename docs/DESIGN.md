# 设计与取舍

## 为什么是浏览器扩展，不是 CDP / Playwright

这类需求最常见的做法是起一个自动化浏览器：登录态、点击、翻页都能写。但它有三个绕不过去的问题：

1. **登录态更脆弱**。脚本要维护一份 cookie 或二维码登录，一旦掉线就得人工介入；扩展直接复用你已登录的浏览器，永远不用管凭据。
2. **它是另一个进程**。操作和你的浏览行为分离，出了问题分不清是页面变了还是脚本错了。
3. **它天然越界**。自动化浏览器能做的事太多，写着写着就会去点、去发——而这不是本项目想做的事。

扩展的代价是权限模型更严、调试更麻烦，但换来一个更小的能力边界：只在你打开的那个页面上，只读。

## 为什么本地规则，不调模型

- **可解释**：每个分数都能说出「命中哪个词、加了几分」。模型给不出这个，只能给一个数字。
- **可复现**：同一份输入永远同一份结果。调规则时能确定「改的是这里」。
- **零成本、零延迟、零网络**：扫描 100 个岗位不需要任何外部调用。
- **隐私**：岗位信息、画像都不出本机。

代价是覆盖不到词表之外的语义。所以设计上把「不认识」的判成**待看**而不是跳过——宁可让你多看一眼，也不要替你误杀。

## 为什么 v2.0 变成只读

v1.x 带过「按节流节奏逐个发起沟通」的能力：点「立即沟通」、把招呼语写进输入框、再用三条证据确认发出去。功能能跑通，但有两个没法回避的问题：

1. **平台协议**。主流招聘平台的用户协议禁止用脚本批量操作。分发一个能自动发起沟通的工具，性质上是「提供工具」，不是「自己用一下」，风险不对称。
2. **它偏离了项目真正的价值**。这个工具好看的部分是规则引擎、结构适配、可解释打分；「替你点按钮」既不难，也不值得展示。

所以 2.0 把整条链路（单次投递、聊天页投递、队列与限流、招呼语模板、投递记录）整体删掉了，不是加开关关掉。代码里不存在，比默认关闭更彻底。

删掉之后，`content.js` 从 1691 行降到 918 行，`tests/flow.test.js` 从「投递全链路」重写成「扫描全链路」，并新增一条断言：**扫描过程中卡片点击次数必须为 0**。

## 为什么零运行时依赖

`devDependencies` 只有 `jsdom`（测试用）。扩展本体没有任何第三方库：

- 面板用 Shadow DOM + 内联 CSS，不需要框架
- 解析用原生 DOM API，不需要 cheerio / 选择器库
- 状态就是一个普通对象，不需要状态管理

好处很直接：没有供应链风险，没有版本冲突，加载即用。代价是所有轮子自己写——但这里需要的轮子都很小。

## 为什么不做的事比做的事多

| 不做 | 理由 |
|---|---|
| 不海投 | 数量换不来面试，只换来账号风险；本工具只帮你筛，投不做 |
| 不绕验证 | 验证码是平台明确的边界，绕过就是把风险从「违约」推向「对抗」 |
| 不伪造环境 | UA / 指纹 / 代理池属于规避检测，性质和前一条相同 |
| 不上传数据 | 没有服务端就没有泄露面，也没有「免费产品的代价」 |
| 不做 OCR / 不做模型 | 纯规则已经够用；引入模型会把「可解释」这条根基拆掉 |
| 不做 E2E | 真实 DOM 每天变，断言它等于给测试埋定时炸弹 |

## 取舍的代价

诚实地说清楚这个项目不擅长什么：

- **换站点成本不低**。`SEL` 表集中是必要的，但每个站点的结构差异仍然要逐个字段调，不是改个域名就行。
- **规则会钝**。偏好词堆到二三十个时，几乎所有岗位都能命中一两个，分数会趋中。建议控制在 10 个以内。
- **不做增量扫描**。每次扫描都是全量重打，页面有 100 多张卡时会有一两秒的卡顿。
